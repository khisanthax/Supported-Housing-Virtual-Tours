# UAC implementation audit and rollout boundary

The current deployed authentication uses opaque HTTP-only sessions, D1 account/revision checks and a separate private scrypt actor. Reuse this architecture. Persisted `editor` maps to the Staff concept without rewriting password records or CHECK constraints. Client is an access context, never a staff account role.

Current published versions are invitation-only. `apartment_visibility` represents withdrawal/archive/removal, not public listing approval. It must not be repurposed as the public-visibility flag. Add a separate default-private approval table with an explicit published revision and approved public metadata. Public routes must query current approval and publication on every manifest, thumbnail and JPEG request with no-store responses; never serve draft manifests or internal metadata. Disabling a listing must not touch private share permissions.

Existing staff APIs assume broad Editor access. Integration must map every route to an explicit action and resource scope, including thumbnail/image reads, draft saves, publication, backup/import, share selection and offline downloads. Upload reservations currently lack owner/apartment scope; add ownership before enforcing restricted writes, rather than letting scoped Staff reuse another apartment's private JPEG IDs. Existing accounts retain operational defaults; new public-visibility management starts denied for Staff. Current generic dashboard queries need scoped filtering before releasing the new policy.

The pure access-policy module is a tested foundation, **not active enforcement**. Role/override/scope state must come from D1, not request JSON, and must be rechecked per request. Add transactional audit writes and guarded optimistic revisions. Administrative role assignment needs an atomic last-active-Administrator guard; the current UI's refusal to modify oneself is insufficient once role assignment exists. Protected account/recovery rights remain locked. Scope restrictions always constrain individual grants.

Before activation: additive schema and rollback-compatible tables; protected Administrator management APIs/UI; endpoint authorization matrix and denial tests; scope-aware staff navigation; isolated public routes/viewer; synthetic publication/withdrawal tests preserving private invitations; browser acceptance and live CPU/quota checks. Never deploy a partially scoped authorization layer.

Private backup: D1 export and KV key inventory are stored under the operator's LOCALAPPDATA/SupportedHousingTour/uac-backup, outside Git. The inventory is not a JPEG-byte backup; retain verified .shtour packages for image recovery, and do not delete KV keys. Existing operator Administrator recovery remains documented in DEPLOYMENT.md. Roll back code/config to the pre-UAC deployment while leaving additive tables in place; do not restore an older database over newer user edits. No live schema, roles, accounts, sessions, visibility or permissions have been changed during this phase.


## Additive database phase

`cloudflare/uac-schema.sql` is deliberately separate from the active schema and has not been applied remotely. `policy-store.mjs` provides validated, revision-checked policy persistence guarded by the current D1 Administrator session; audit triggers commit together with policy changes. Last-Administrator guards reside in SQLite so simultaneous demotions cannot remove the final active administrator. Public approval rows start absent and do not modify existing withdrawal state or private invitations. The migration was applied twice to the private restored backup without changing any existing table's contents. This does not yet authorize activating policy writes: complete scoped route enforcement and management integration first.


## Opt-in Worker integration (12 November)

The branch now connects request-policy enforcement and the Administrator policy API only when `TOUR_UAC=1`. This flag is absent from the live pilot; do not enable it for production testing yet. There is no migration auto-run. Local tests explicitly apply the additive schema before opting in. The endpoint matrix covers direct resource reads/writes, mixed-scope invitation management and filtering; uploaded-photo ownership is recorded and draft saves validate authorized references. Remaining work includes the user-facing permission interfaces, public Client viewer routes and approval management, complete operation-specific export/import/private-view semantics, role-assignment/audit integration and live migration/rollback/browser/CPU acceptance. This remains an incomplete draft, not a released permission system.
