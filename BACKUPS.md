# Encrypted apartment backups

In the Gallery, open **Manage apartment → Export .shtour**, or choose **Export Backup** in the editor. Enter and confirm a unique backup password of at least 12 characters. **Encrypt and Download** creates `apartment-backup.shtour.zip`. Store the file in agency-approved backup storage, rename it with an apartment reference/date if appropriate, and keep the password separately in approved secure storage. The app cannot recover a lost password. Do not reuse staff login passwords or guest phrases.

To restore, open **Backups and storage**, select the ZIP, and leave **Import as → New apartment** selected. Enter its backup password when asked. The app authenticates/decrypts and validates the complete tour locally before uploading its photographs through existing authenticated APIs. A new restore is a private draft. Verify every viewpoint, name and doorway, export a fresh backup, and publish only with the required approval. Restoring over an existing apartment requires explicit confirmation and the current cloud revision; existing guest publication remains unchanged until explicit publication. The editor's Import Backup also confirms replacement of its current private draft.

Older unencrypted `.shtour` files still import without a password. New UI exports always encrypt; there is no plaintext export option. Existing plaintext packages remain sensitive: protect or retire them under agency policy. Wrong passwords and authentication failures deliberately share one error because ciphertext damage cannot always be distinguished from a wrong key. Cancel/retry safely; no partially downloaded archive is offered, and failed validation never commits a partial apartment. A failed cloud upload can leave reserved/unreferenced photos for the existing safe cleanup workflow, but cannot change a published tour.

## Format and security

This is an app-restorable encrypted ZIP container, **not a WinZip-password-compatible archive**. ZIP contains only `encryption.json` and `apartment.bin`. AES-256-GCM encrypts the entire original `.shtour` payload, hiding photo bytes, room names, coordinates, recovery checkpoints and tour metadata. Its 128-bit authentication tag covers the payload and exact encryption metadata as additional authenticated data. A fresh cryptographically random 128-bit salt and 96-bit nonce are generated for each export. PBKDF2-HMAC-SHA256 derives a 256-bit key with 600,000 iterations. No weak ZipCrypto or WinZip's low-iteration password derivation is used.

Encryption uses the established, externally reviewed **noble-ciphers** library's native Web Crypto wrapper; ZIP packaging uses **fflate**. Pinned versions, licenses, upstream audit reference and build provenance are in [vendor notes](dist/vendor/BACKUP-LIBRARIES.md). The upstream audit does not constitute an independent audit of this application's integration or every newer upstream version. PBKDF2 parameters follow the [OWASP reference](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). HTTPS or localhost and Web Crypto support are required; unsupported browsers fail rather than export plaintext.

Only fixed, uncompressed ZIP entries are accepted, with bounded file/count/expanded-size checks. ZIP compression, nested/extra/duplicate/unsafe entries and unsupported encryption versions are rejected. Original package limits remain 12 viewpoints / 160 MiB total JPEGs; existing cloud limits remain 4 MiB per JPEG. Large exports can require substantially more browser memory than file size; close other tabs and retry on desktop if a mobile browser runs out of memory. Cancellation suppresses output even when an already-running native crypto operation cannot be interrupted.

Passwords are never sent to Cloudflare, analytics or logs, saved in browser storage, or included in the archive. Fields are cleared after submission/close. Derived key and plaintext byte buffers are cleared when possible; JavaScript strings and browser internals cannot guarantee memory erasure. Authenticated restoration still uploads decrypted data to the existing private cloud storage; this feature encrypts **exported backups**, not D1/KV at the application layer. Malware, extensions or an unlocked authorized device remain outside its protection.

## Coverage and recovery

A package preserves original JPEG bytes, names, viewpoints, starting room, grid, arrows, connections and applicable draft/recovery metadata. Deliberately incomplete private drafts remain incomplete on restoration; they are not silently published. Packages do **not** include staff accounts/passwords, role policies, apartment identity assignments, guest invitations/permissions, audit history, server secrets or a complete publication/version history. A new restore receives a new apartment identity and no transferred invitations.

Export after meaningful editing and before replacement/removal; retain several dated generations under agency policy and rehearse a restore into a separate private apartment. Keep passwords separately accessible to authorized recovery staff. Full disaster recovery also requires private D1 exports, retained immutable KV JPEGs and securely held deployment secrets/configuration; see [deployment](DEPLOYMENT.md) and [recovery](RECOVERY.md). A KV key inventory alone is not a photo backup. No backup, plaintext credentials or real agency photographs belong in public GitHub.
