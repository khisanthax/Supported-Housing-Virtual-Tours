## Physical rotation report: recovery and full-viewport revision

The owner reported a Fold 7 failure when upward aiming caused screen rotation. Investigation found reproducible code defects: the opening screen angle was treated as immutable, camera restart rejected other angles/aspect shapes, and the untracked fallback projected the target at the crosshair centre. Saved photos were intact, but selecting dots could not restore tracking/calibration. These explain the simulated failure paths; they do not prove the exact sequence of physical sensor events on that phone.

Resume Capture now reconnects the camera and orientation listener, samples the current display angle and requires fresh sensor movement before saved-photo realignment. Unknown tracking hides the target instead of drawing false alignment. Rotation/background/camera interruption pause capture without closing the session. Completed target IDs persist; unfinished dots select the next target, and only an explicit retake replaces a completed photo. Inverted camera aspect uses a correspondingly inverted field of view per frame; other unexpected framing changes produce a recoverable error rather than guessed crop geometry. Pending camera requests are invalidated on pause/close.

Capture uses a full-window dialog with persistent Pause/Resume, Retake, Settings, Realign, Fullscreen and Exit controls. The Fullscreen API is optional, invoked through a user gesture on the document element; the native dialog itself cannot be the fullscreen target. Leaving fullscreen leaves the full-window fallback usable. No orientation lock is required. Video uses contain fitting, and the target projection uses exactly the contained video rectangle. Letterboxing remains when the native camera frame and display differ; it is never stretched/cropped to fake coverage. Safe-area padding and portrait/landscape sizing are included.

Run `node capture/recovery-browser-test.mjs` for rotated-angle resume, fresh-movement calibration, stale target hiding, remaining-target projection, refresh recovery, camera interruption, simulated background/resume, folded/unfolded/landscape geometry, Fullscreen entry/exit and API-unavailable fallback. Existing guided full-sweep and capture/stitch/editor/offline/encrypted-backup tests remain required. Simulated events and fake cameras are not physical acceptance. A sensor that continually emits identical valid values is indistinguishable from a truly stationary phone without another independent signal; the movement check prevents confirming a resumed frozen stream, but cannot certify all hardware sensor failures. Slow drift still needs matching the saved reference image.

No stitching engine was replaced: this revision improves capture/UI reliability, not feature matching, exposure equalization, seam optimization or optical calibration. The licensed OpenCV and Stanford permission investigations below remain the next engine-quality options; no new dependency was adopted.

Fold retest: open the temporary HTTPS site in Chrome, capture several wall photos, tilt/roll until the screen rotates, then Resume Capture while still rotated. Move gently to prove tracking, choose Realign, match the saved starting photo, select an unfinished dot and continue. Repeat after backgrounding, closing/reopening and refresh; confirm completed count stays unchanged. Test folded/unfolded and landscape, retake one photo, exit fullscreen, then stitch/inspect/export. Record browser/device behavior and visible seams. Physical Fold 7 acceptance remains open until this retest passes.

## Visual guidance update (PR #49)

Start rear camera, allow motion guidance, hold the phone upright and follow the empty circle with the fixed centre crosshair. Once alignment remains steady for at least 800 ms with fresh sensor samples, capture happens automatically. The next target highlights immediately. Coverage dots show saved photographs and let you select an individual retake. Progress reads “12 of 37 photos captured” (the actual total adapts to camera shape). New plans start level, sweep horizontal rows and include ceiling/floor. No degree entry or numeric aiming is exposed. The standard rear-lens field of view remains an internal experimental assumption, not automatic calibration.

Screen-relative camera axes are corrected for the initial display orientation. Changing orientation during capture safely pauses the camera; return to the original orientation and realign against the saved starting photograph. Resuming a session also requires this visual-reference realignment. Sudden sensor discontinuities pause guidance. **Slow sensor drift cannot be detected or corrected automatically without visual alignment**; use the starting-photo realignment control whenever the circles drift. This depends on the user matching the reference scene accurately.

Movement, stale samples, backgrounding and in-progress saves block automatic capture. A consumed target cannot capture again without explicitly selecting a retake. ## Stanford findings and reuse decision

[Stanford's About page](https://vftcam.stanford.edu/about.html) describes guided sensor capture and local WebGL processing. Its footer reserves rights. The bounded first-party/repository search found technical documentation but **no verified application source license granting modification/redistribution**. Publicly delivered JavaScript and published snippets are not permission to incorporate them. No Stanford code, shaders or assets were copied. Reusable-component permission and a supported integration API remain unverified; no documented embeddable SDK was located.

[The technical description](https://vftcam.stanford.edu/building-vftcam.html) describes browser camera/sensors, ES modules, WebGL2, local browser storage and equirectangular JPEG export. It lists Three.js, Pannellum, piexif, Workbox, icons and JSZip despite its dependency-free wording. Their individual licenses do not license VFTCam itself. It reports Android/iOS support and fast phone processing; those are vendor claims, not our measurements. The article's code samples were not reused.

[Stanford's privacy policy](https://vftcam.stanford.edu/privacy-policy.html) says capture, stitching and storage occur on-device and distinguishes optional location/maps behavior. This is documentary evidence, not a network audit of the current application. Exact deployed dependencies, offline operation, export metadata, output quality and programmatic reuse would require permission and version-specific inspection. We have not benchmarked Stanford side-by-side.

Do not expand this simple blender into an unbounded substitute for mature stitching software. No uncertain-license dependency is installed by this branch.

## Architecture and guardrails

- Capture permission is requested only by Start rear camera. Rear camera is requested as a preference, not guaranteed by browsers. Sensor permission is a separate gesture where the API requires it. Camera access needs a secure context: [camera API requirements](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).
- Independently implemented pinhole/rotation math follows the [W3C orientation coordinate conventions](https://www.w3.org/TR/orientation-event/). Device lens offset, FOV and drift are not calibrated automatically. Manual aiming is explicitly labeled estimated. Sampled angular coverage cannot detect blurred frames or mistaken aiming.
- Adaptive capture plans include both poles and typically use 37–49 photos depending on aspect/FOV (38 for the synthetic portrait fixture). Per-session limits are 64 frames and 64 MiB source JPEGs. IndexedDB transactions reject stale writes; failed writes keep the previous record. Browser quota/eviction is not a permanent backup guarantee.
- Worker reprojects and feather-blends one decoded image at a time into a full sphere. Any uncovered output pixel causes failure instead of fabricated content. Cancel terminates the worker; source JPEGs survive. Backgrounding stops processing/camera; orientation changes stop capture and require the original orientation. No service processes photographs remotely.
- Outputs are standard 2:1 JPEGs at explicitly chosen resolution/quality. No XMP/EXIF compatibility claim. Existing 4 MiB/8192×4096 limits remain unchanged. Oversized output is rejected with instructions, never silently recompressed. Sparse synthetic imagery fits easily; detailed/noisy real 4096 panoramas may not. Do not increase production limits without representative phone JPEG/storage tests.
- A capability-gated hook in the existing guided editor receives an approved JPEG, validates it, checks duplicate bytes and uses the existing revision-checked draft save. It does not replace the editor/viewer. Production runtimes define no capture capability, so no Capture Room control appears there.
- The isolated build injects that capability only into a staged Local Only runtime. It caches all capture assets under a distinct service-worker cache. Existing Local Only network blockers/CSP remain; server only accepts GET/HEAD. There are no upload endpoints.
- The shared hook also works with a capability-enabled Cloud runtime and checks edit/upload capabilities before using existing storage. Its approval wording explicitly names upload. **Authenticated capture-to-Cloud acceptance passed against the actual Worker with isolated in-memory D1/KV adapters**: no upload before approval, exactly one completed JPEG afterward, new private revision, unchanged prior version, reload and anonymous upload denial. No live capture upload was tested or enabled. Run the existing migration browser harness with `CAPTURE_TEST=1` and its synthetic encrypted-backup fixture to reproduce. No raw-frame API exists.

## Measurements and acceptance boundaries

Desktop Chromium, 38 generated 360×480 perspective JPEGs with exact known poses; smooth analytic environment with high-contrast angular lines. This deliberately easy fixture is not representative indoor photography. Increasing output size does not create additional source detail.

| Output / quality | Output bytes | Observed worker time (representative run) | Estimated major working allocations |
|---|---:|---:|---:|
| 1024×512 / 92% | 125,936 | 0.46 s | 40.0 MB |
| 2048×1024 / 92% | 285,164 | 1.47 s | 71.4 MB |
| 4096×2048 / 92% | 665,515 | 4.72 s | 197.3 MB |
| 2048×1024 / 70% | 146,982 | 1.40 s | 71.4 MB |
| 2048×1024 / 98% | 525,173 | 1.41 s | 71.4 MB |

Times vary with desktop load and headless graphics; not mobile benchmarks. Memory numbers are array/decode estimates, **not measured peak process/GPU memory**. JPEG encoding, browser copies and the viewer can add substantial memory. Sensor capture duration and phone thermal stability were not measured. Synthetic absolute RGB error at 1024/92% was 5.68/255; alternating 0.8/1.2 exposure increased it to 18.10/255. This quantifies a limitation, not a perceptual indoor quality certification. Known-pose lines can still show resampling/feathering softness; pose errors, parallax and moving subjects can duplicate objects and create severe seams. Those real-world defects have no automatic repair here.

Verified locally: all 108 regression tests; capture-session persistence/stale-save/bounds tests; full existing Local Only browser flow including encrypted backup/recovery; new capture acceptance, exact JPEG/tour encrypted-backup roundtrip and browser-process restart; offline worker stitching; analytic coverage rejection; zero external/non-GET requests; responsive dialog checks at 412/768/1104 px; fake camera gesture/retake/reload/track-stop checks. Screen simulation is not physical Android acceptance. Synthetic permission denial is injected in a browser test, not an OS-level permissions test. Actual quota exhaustion/OS termination, WebKit, iPhone/iPad and physical camera quality remain unverified.
