# Development and deployment

For local Worker testing, run these commands from the repository root in separate terminals as needed.

```powershell
node cloudflare/prepare.mjs
npx --yes wrangler@4.157.0 d1 execute DB --local --config cloudflare/wrangler.jsonc --file cloudflare/schema.sql
npx --yes wrangler@4.157.0 dev --local --config cloudflare/wrangler.jsonc --ip 127.0.0.1 --port 4193
node cloudflare/probe.mjs
```

The asset preparation script creates local development secrets in the ignored cloudflare/.dev.vars. Keep separate credentials for local and hosted environments. Use an ignored cloudflare/wrangler.pilot.json with the approved Worker name, D1 database and KV namespace. Set the exact HTTPS pilot origin, turn off preview URLs, and keep the pilot isolated from production housing data. Configure secrets through Wrangler. Never put them in Git or shell arguments. Inspect and back up the existing database before applying schema updates. Deploy only synthetic test data to the approved pilot.

Before deploying, confirm the Workers plan is Free, and check account-wide Workers, D1 and KV usage. Keep R2 and other paid products disabled. Verify signed-out routes, guest scope and revocation, JPEG retrieval, and CPU observations after deploy. Cloudflare quotas apply across account workloads.

## Individual staff accounts

### Self-contained staff passwords

Set `STAFF_AUTH_MODE=password` on the synthetic pilot after applying the additive D1 schema. This setting enables individual accounts and requires the existing private `STAFF_LOGIN` binding. Sign-in and credential changes use a single instance for synchronous password work. A separate instance serves the staff dashboard and account list. The public Worker validates the origin and forwards only the allowed routes. The password flow makes no identity-provider calls.

The credential actor uses native scrypt with `N=32768, r=8, p=3`, a unique 16-byte salt and a 32-byte verifier. This is an OWASP-listed 32 MiB profile. Native Argon2 is unavailable in Workers. Scrypt uses a 48 MiB per-call allocation limit and runs one derivation at a time per isolate. New passwords require at least 15 characters and fit within 256 UTF-8 bytes. D1 stores salted verifiers, roles and revision numbers. The one-hour session uses a separate random cookie with `Secure`, `HttpOnly`, `SameSite=Strict` and `Path=/`. D1 stores only the session token digest. The username and source buckets each allow eight attempts per minute, with a shared ceiling of 32 derivations per minute. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt) · [Cloudflare crypto support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/)

Bootstrap the first synthetic Administrator from a trusted terminal. Pipe the password into `node cloudflare/bootstrap-password-admin.mjs USERNAME` using redirected stdin from an approved secret store. Capture its output in a private temporary SQL file and apply that file to D1. The statement inserts only if the local account table is empty. Treat the verifier file as sensitive and delete it afterward. Subsequent account creation and resets happen in **Manage staff accounts**. Give staff their initial or reset password privately. Resetting or disabling an account invalidates its sessions immediately. The pilot has no public registration or reset endpoint.

Apply the additive schema before deploying. Keep the last working Firebase Worker version, its secrets, and its D1 tables available for rollback. Password mode uses separate tables and cookies, so restoring the previous Worker selects the old credentials and requires a fresh sign-in when the browser has no valid cookie for that mode. Keep the Durable Object class and binding across deployments. Use a new object name when a change makes the public Worker forward a route that an older instance would reject. The credential data lives in D1 and follows neither object name nor instance. No Firebase password migration is needed.

For synthetic acceptance, require the public Worker p95 at or below 8 ms and maximum at or below 10 ms. For password derivations in the private object, target p95 at or below 750 ms and maximum at or below 1 second with zero CPU and memory errors. These are pilot performance targets within the platform limits. Capture both layers during sequential and concurrent use and distinguish the scrypt workspace from measured isolate memory. Workers Free gives a SQLite-backed object a 30-second default CPU budget, 128 MB per isolate, 100,000 requests and 13,000 GB-seconds per day, and 5 GB total SQLite storage. [Cloudflare limits](https://developers.cloudflare.com/durable-objects/platform/limits/) · [Cloudflare pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)

### Firebase rollback configuration

Create a dedicated Firebase Spark project with Analytics disabled and enable Email/Password as its only sign-in provider. Use Firebase Authentication settings to disable end-user signup and deletion. Before enabling staff accounts, verify that a direct signup request with a synthetic identity returns `ADMIN_ONLY_OPERATION` or the equivalent admin restriction. Verify that the project is still on Spark without a billing account. [Firebase pricing](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans) · [Firebase user self-service settings](https://firebase.google.com/docs/auth/users#user_self-service)

Create the first synthetic user in Firebase Authentication. Apply the additive D1 schema, then run `node cloudflare/bootstrap-admin.mjs USERNAME FIREBASE_UID FIREBASE_EMAIL` on a trusted terminal. Apply its output to D1 using a private temporary SQL file. The SQL is guarded so it only bootstraps an empty Firebase staff account table. Set `FIREBASE_PROJECT_ID` in the ignored pilot configuration and set `FIREBASE_AUTH_API_KEY` through Wrangler secrets. Use a key restricted to Identity Toolkit. Keep the username mapping and key server-side.

Enable `STAFF_ACCOUNTS=1` for the synthetic acceptance deployment. Firebase checks passwords. At sign-in, the Worker verifies the Firebase token signature, project, expiry, provider and UID. It issues a random 256-bit session ID, stores only its digest, and discards Firebase ID and refresh tokens. Each protected request checks the D1 session digest, expiry, current role, enabled flag and account revision. Sessions expire with the Firebase token, typically after one hour. Older cookies that include a Firebase token still verify that token until their session expires. Login is rate limited by source address and normalized username. Writes require the app origin and session cookies are HTTP-only, SameSite Strict and Secure on HTTPS.

After bootstrap, create additional users in Firebase Authentication and link their UID and email under **Manage staff accounts** as an Administrator or Staff Editor. That page can send Firebase reset emails and disable or re-enable app access. A reset requested there or a disable invalidates existing app sessions. Direct changes in Firebase do not revoke an already issued app session immediately. Disable the app account in D1 when immediate revocation is required.

### Private staff sign-in on Workers Free

Set `STAFF_LOGIN_BACKEND=durable-object` to send named staff sign-in and dashboard requests through the private `STAFF_LOGIN` binding. Copy the `durable_objects` binding and SQLite migration from the local Wrangler configuration to the ignored pilot configuration. The public Worker validates the pilot and checks the sign-in origin. For sign-in, it replaces the internal client address header with the Cloudflare ingress address. One object runs the existing D1 rate checks, Firebase sign-in and signed-token validation, and guarded session creation. A separate instance verifies the current D1 session and reads the dashboard inventory. Neither instance has a public route or writes credentials, sessions, or application data to Durable Object storage. Other staff and guest routes continue to use D1 from the public Worker.

Deploy the additive class migration first with `STAFF_LOGIN_BACKEND=worker`. Verify that version and retain it as the rollback target. Then deploy the enabled version. If sign-in fails, roll back to the version that already includes the class. Cloudflare restricts rollback across class migrations. Stay on Workers Free and check account-wide usage. The SQLite Durable Object allowance is 100,000 requests and 13,000 GB-seconds per day. Its default CPU budget is 30 seconds per invocation. The public Worker still has a 10 ms CPU limit. [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/) · [Free quota](https://developers.cloudflare.com/durable-objects/platform/pricing/) · [Rollback restrictions](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/#bindings)

Before enrolling real staff, test valid and invalid credentials, signup denial, reset delivery, logout, session expiry, disabled accounts and cross-browser roles with synthetic accounts. Verify guest unlock and staff route isolation. Capture separate Cloudflare CPU samples for the public Worker and the private objects on sequential and concurrent login and dashboard requests. For public Worker sign-in and protected API calls, require p95 at or below 8 ms, maximum at or below 10 ms, and zero runtime errors. For the private objects, require p95 at or below 25 ms, maximum at or below 100 ms, and zero runtime errors as pilot performance targets. Record sample counts and telemetry gaps. Measure cold and warm requests separately when isolate state is known. Local tests and mocked Firebase responses cannot establish live CPU or Firebase project configuration.
