# Diagnostics, activity history and support

Administrators open **Diagnostics** from the staff navigation. Staff can provide the `VT-…` operation reference shown after a failed request; they cannot read diagnostic records or change logging settings. The existing UAC Access History remains the durable business/security audit. New detailed rows link to its audit row ID where an audited server action exists. Browser milestones are supplementary, untrusted observations, never proof of server commitment.

Search by exact operation ID/error code/username/apartment ID and filter category, severity and time. Apartment filtering includes direct apartment operations, recorded requested multi-apartment scope and current invitation membership. Current membership is a search association, not proof of historical permissions after a link was edited; inspect the recorded scope/audit timeline for that. Click a result to load all retained spans for that operation in chronological order. Each span has its own ID and optional parent, source, version/build/deployment, elapsed time, failure stage, result/saved classification, retry flag and sanitized milestones. Browser upload/editor/import actions pass their root ID through API/authorization/storage/database stages and across private Worker/DO boundaries. Numeric file sizes/dimensions/counts are allowed; filenames, field contents and images are not.

**Export Diagnostic Report** downloads a portable ZIP containing `diagnostic.json`, format `virtual-tours-diagnostic`, version 1. It contains the selected retained timeline and a safe configuration summary, not the database, passwords, cookies, tokens, guest phrases, encryption keys, photographs or backup contents. It can contain staff usernames and internal apartment/deployment IDs: treat it as internal operational data and review it before sending it through an agency-approved ticket channel. Exported reports are plaintext; use approved storage/transport. No external monitoring/analytics/ticket service is connected.

Codes distinguish authorization, expired/disabled sessions, invalid input, stale revision, rate/capacity limits and observed database/storage exceptions. Runtime exceptions are mapped to safe fixed messages. Unknown causes remain **unknown**. A 503 alone does not prove KV delay, CPU exhaustion or quota exhaustion. Browser-reported timeout/failure events may be absent if the browser stays offline or closes; a Worker terminated before completion cannot log its own final outcome. Inspect Cloudflare's private tail/usage for actual CPU/runtime failures. UI timings are wall time, never CPU measurements. Missing records do not prove an operation never happened.

## Limits and retention

Default level normal, seven-day retention and 2,000 retained detail rows; Admin may select off/error/normal/detail, 1–30 days and 100–10,000 retained rows. SQL enforces at most 2,000 inserted detail rows per UTC day even if old rows are deleted. Client batches allow at most 24 known milestones/8 KiB, authenticate and scope-check, and rate-limit by account. Normal spans retain up to 16 milestones plus their summary; detail retains up to 24. DB timings aggregate and cap repeated entries. Successful diagnostic queries do not log themselves. Successful image GET detail is sampled at approximately 10%; errors and mutations remain eligible until the daily cap. Unknown sign-in usernames are not persisted, avoiding accidental credential entry in that field.

Insert-trigger cleanup removes up to 100 obsolete detail rows per new record; expired rows can remain while idle/off or when the daily cap stops inserts. Cleanup is opportunistic rather than a background scheduler; the hard row/daily bounds prevent runaway growth. Existing long-term activity/policy history is not deleted by this retention. Diagnostics deliberately never turn a committed apartment save into an error if detail recording fails; a missing schema, D1 quota or cap may leave gaps. Lower detail to error for busy workloads. Index updates, cleanup and daily counters also count against D1 rows written; monitor account-wide usage rather than treating 2,000 log entries as only 2,000 billed writes. No paid telemetry is enabled. New installations disable platform invocation logging; the pilot also uses this setting to avoid retaining unrestricted platform request metadata. Use the on-demand safe CPU collector for redacted timing measurements, never attach raw tails.

## Self-service and future tickets

Help at `/staff/help` explains sign-in, apartments, uploads, doorways, review/publication, guests, permissions, backups, Migration and common codes. Onboard an Administrator by verifying version, a second recovery Administrator, safe backup storage, synthetic restore and scoped Staff account. Onboard Staff with a private temporary credential, assigned apartment access, one synthetic upload/doorway/preview, Copy Invitation and encrypted backup rehearsal. Follow STAFF.md/PILOT.md; do not enroll real identities without authorization.

A future asynchronous ticket should include app/build/edition, operation ID, approximate time/timezone, expected/actual behavior, reproduction steps and a reviewed diagnostic ZIP/screenshot. Never include credentials, original photos or backup/password pairs. No ticket service, phone line, live chat or response guarantee is created. Optional future paid setup/training/troubleshooting requires a separate owner policy; normal independent agency use must not depend on purchasing support.
