# Help Hub deployment plan

## Host and access

Run a reviewed Phase B build on one owner-managed host with a dedicated service identity and a private, encrypted state directory outside the repository. Place the Hub behind a TLS gateway. Keep Node and SQLite supported and patched. Start with one operator and one fictional agency. Keep direct agency support available during a Hub outage.

| Route | Access |
| --- | --- |
| `/agency/tickets` | Registered Workers over HTTPS. One unique bearer per agency and an exact HTTPS installation origin. Allow GET and POST. |
| `/mcp` | Owner-controlled private connection. Configure the distinct MCP bearer using an OS secret manager or protected launcher. |
| `/owner/approve/` | Loopback on the Hub host. Use a separate approval credential and a five-minute approval for the exact ticket. Exclude the entire owner path at the gateway. |
| All other paths | Reject at the gateway. |

Use distinct gateway routes for agency intake and owner MCP. A named Cloudflare Tunnel on an approved existing zone is one option for stable agency intake. A private connection to the owner host can keep MCP away from public ingress. Treat the existing Quick Tunnel rehearsal as disposable evidence. Confirm plan eligibility and configuration before provisioning any stable resource. [Cloudflare Tunnel documentation](https://developers.cloudflare.com/tunnel/)

Set body and connection limits at the gateway. Use a rate budget per client or credential where available, with independent budgets for the two routes. The Worker still enforces agency approval, grant scope, expiry and revocation. Limit gateway diagnostics to route category, status, timing and a request ID generated by the gateway. Exclude credentials, cookies, headers, URLs with query strings, and request and response bodies from access logs, traces and error reporting. Verify the provider's logging configuration as well as the application process.

Run the Hub and Codex in separate process environments. The Codex launcher gets only the owner MCP bearer, while the Hub gets the encryption key, registration credentials and approval credential. Apply and verify this filter in the operator's Codex configuration. [Codex configuration reference](https://developers.openai.com/codex/config-reference)

```toml
[shell_environment_policy.filters]
"LT360_HUB_*" = "exclude"
```

On the selected operator host, use a supported Codex sandbox and run `node help-hub/operator-acceptance.mjs` with Node 24 and Codex installed. An optional final argument selects a particular Codex executable. The synthetic check authenticates MCP, verifies the bearer is absent in a sandboxed child, and verifies that a file write remains blocked. On Windows, Codex in Ubuntu WSL2 with its Linux Bubblewrap sandbox is a supported option. [Codex in WSL2](https://learn.chatgpt.com/docs/windows/wsl)

Rotate the owner MCP bearer, owner approval secret and agency secrets independently. Use the Hub's documented transactional encryption-key rotation procedure. On suspected compromise, revoke the affected grants at the agency Workers, replace the credentials, and verify the retired credentials are rejected before resuming intake. [Help Hub operator guide](README.md)

## Data, backup and recovery

Start with technical-only tickets. Admit data categories explicitly approved by the agency and service owner. Keep resident names, housing addresses, pictures, credentials and private logs out of ticket and note text. Approve which diagnostic or apartment details may be sent to the authorized Codex environment before allowing any real-data support.

Audit events and closed tickets have a 30-day Hub retention window. Stop the Hub for the pilot backup or restore. Use an independent 256-bit base64url backup key from the protected `LT360_HUB_BACKUP_KEY` environment variable. The helper authenticates and encrypts the whole SQLite archive and refuses to overwrite a destination or recover an archive older than 30 days. Run it from the protected host with the source and isolated destination on private encrypted volumes. Store archives separately with 30-day provider-side expiration and keep recovery keys separate. Log completion and the recovery receipt without ticket content or secrets.

```sh
node help-hub/backup.mjs backup HUB_DATABASE NEW_ARCHIVE
node help-hub/backup.mjs restore ARCHIVE NEW_ISOLATED_DATABASE DELETION_LIST_JSON
```

Keep a protected JSON list of manually purged ticket references outside the Hub database until all snapshots that could contain them expire. Scope the list to the same Hub database, even when it is empty. During recovery, stop intake and restore to an isolated copy. The helper clears old credentials and approvals, closes pending and active tickets, and reapplies the deletion list and retention cutoff. Separately revoke previously issued grants at each agency. Require a fresh grant for new access. Verify that an old key or session cannot be used through the recovered Hub, and that approved history remains readable before connecting it to an intake route.

## Pilot gates

1. Record the approved hostname, host owner, operator, agent data boundaries, retention owner, and alert contact. Check DNS, TLS and route isolation while using synthetic data.
2. Verify agency and operator bearer isolation, operator shell exclusion, approver isolation, key rotation, revocation, and zero sensitive canaries in the production gateway and platform logs.
3. Rehearse a stopped-service encrypted backup and isolated recovery. Verify deletion records are applied and retired activation keys and sessions stay unusable. Confirm backups age out from the chosen storage provider.
4. Rehearse an outage and verify that the agencies can continue and use independent support keys. Establish the operator's rollback to the prior reviewed build. Leave the real-data gate closed until the service owner accepts the evidence.

## Approvals

- Approve the exact stable host, hostname and network routes before creating permanent infrastructure or using a production account. Approve any cost separately.
- Approve the operator and agency data boundaries, organizational ownership of recovery keys and the retention and deletion policy before accepting real tickets.
- Approve changing the shared Option A development ref before applying the prepared backport to PR #52. The PR merge and publication of a regenerated template remain separately controlled.
- Approve either PR merge, release publication, and final removal of the disposable Workers or detached storage separately.
